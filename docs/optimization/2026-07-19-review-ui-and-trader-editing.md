## OPT-001 Define Review/K-line Control Ownership And Unify The Control Surface

- Source evidence: the user-provided 2026-07-19 Chrome screenshot shows the K-line engine's built-in toolbar and the Review page's historical bottom toolbar at the same time. `frontend/src/kline/kline-engine.js` already owns timeframe, replay navigation, playback speed, zoom, follow mode, MA/VWAP overlays, candle type/fill, and theme. `frontend/src/pages/ReviewPage.jsx` repeats `1m`, `5m`, Back, Step, Play/Pause, and Overview outside the engine, while also mixing those chart operations with Review-owned `Market day`, Strategy, Ext K/RTH, Backtest, Rescan, and status controls. The left Ticker/Date trade-record filters add a third context-looking surface even though the bottom `Market day` selector changes the assembled chart/review day.
- Current friction: the problem is not only visual density. Two components currently present overlapping authority over the same chart state, so users cannot tell whether an action belongs to the reusable chart engine or to Daily Review. Generic chart controls are duplicated, while business context and chart-local operations are interleaved in the same outer bar. Repeated ticker/date surfaces further obscure which state owns the chart, signals, trader markers, and exports.
- Control ownership decision for future planning:
  - K-line engine owns generic chart interaction: timeframe, replay Back/Step/Play/Pause, speed, zoom, follow/fit/overview, indicator visibility, candle rendering, and theme.
  - Review owns business context and workflow: market day (ticker/date), strategy, Ext K/RTH data window, trader/eligibility/focus filters, Backtest, Rescan, trade-record export/selection, and assembly/error status.
  - Review passes resolved context/data/options into the engine and consumes engine events; it should not render a second button for a generic operation already exposed by the engine.
- Desired outcome: one coherent Review control surface makes market day, strategy, session window, and business filters authoritative, while the K-line engine remains the single home for reusable chart operations. Trader overlays derive ticker/date from the selected market day unless a real cross-day comparison mode is explicitly designed. The chart, stats, signals, trader records, and exported selection visibly reconcile to the same Review context.
- Acceptance direction: every visible control has one named owner and appears once; changing Review context refreshes all dependent business data without resetting unrelated engine preferences unless explicitly required; generic engine behavior remains reusable in Review, Backtest, and Teaching without page-specific duplicate controls; narrow and collapsed layouts retain the same ownership model.
- Accessibility risk: duplicated actions and overlapping context selectors create ambiguous labels, reading order, and focus destinations. Consolidation should retain programmatic labels, expose current state once, announce Review loading/state changes, and preserve keyboard access inside the engine; screenshot evidence alone cannot verify keyboard or screen-reader behavior.
- Boundary that must not change: do not weaken current market-day assembly, normalized trade filtering, export reconciliation, or SQLite/data safety contracts.
- Lifecycle status: proposed via [`Tang Strategy Review Workspaces And Trader Point Editing`](../exec-plans/proposed/2026-07-19-tang-strategy-review-workspaces-and-trader-point-editing-plan.md); review-only

## OPT-002 Make Trader-Point Editing Discoverable And Task-Oriented

- Source evidence: the screenshot shows a collapsed icon-only global navigation with no visible trader-editing label. `frontend/src/components/Layout.jsx` exposes `Traders` only when `role === 'admin'`; readonly users receive no visible explanation that the workspace exists or requires admin access. `frontend/src/pages/AdminTradersPage.jsx` provides two raw JSON textareas (`Trader registry JSON` and `Daily record JSON`) rather than a point-oriented editing flow.
- Current friction: the user cannot find a page for editing trader points. Even after reaching the admin workspace, the current raw JSON contract requires prior schema knowledge and does not map naturally to the review task of selecting a trader/day, locating a point, and adding or correcting its event details.
- Desired outcome: the navigation makes the trader-record workspace and its permission state explicit. An admin can enter a clear `交易记录 / 点位管理` flow, choose ticker/date/trader, inspect existing groups/events against the chart, add or edit a point with field-level validation, preview the candidate, and only then save through the existing validated atomic path. A readonly user sees a clear non-editable inspection state and how admin access differs, without exposing credentials.
- Acceptance direction: an authenticated user can determine within one navigation action whether editing is available; an admin can locate a day and point without editing raw repository JSON; save remains validation-first and failure leaves canonical content plus DB projection coherent.
- Accessibility risk: icon-only navigation relies on hover/title discovery and the raw JSON editor has weak task instructions and error recovery. A future flow should preserve visible labels in collapsed navigation through an accessible disclosure pattern and provide field-level errors/focus management; keyboard and assistive-technology behavior still require interactive verification.
- Boundary that must not change: admin-only mutation, schema validation, candidate projection, atomic content replacement, rollback coherence, and secret/auth boundaries remain mandatory. This record does not authorize a new route, editor implementation, login change, or data write.
- Lifecycle status: proposed via [`Tang Strategy Review Workspaces And Trader Point Editing`](../exec-plans/proposed/2026-07-19-tang-strategy-review-workspaces-and-trader-point-editing-plan.md); review-only

## OPT-003 Separate SPY And QQQ Browsing Workspaces

- Source evidence: the user-provided 2026-07-19 Data-page screenshot shows SPY and QQQ market days interleaved in one reverse-chronological list. `frontend/src/pages/DashboardPage.jsx` renders the first 20 items from the shared `state.marketDays` array without ticker partitioning. Review likewise renders every ticker/day in one flat `Market day` selector, while the shared app state has a selected day but no explicit selected-ticker context.
- Current friction: as QQQ coverage grows, mixed-symbol lists and selectors become increasingly difficult to scan. The ticker is repeated on every row/option, dates for different instruments compete in the same navigation surface, and users can unintentionally cross from an SPY task into a QQQ day without a clear workspace transition.
- Desired outcome: Data and Review establish SPY or QQQ as an explicit parent context before presenting dates. The Data page lists and summarizes only the selected ticker's market days by default. Review carries the same ticker context and offers only valid dates for that ticker; strategy and trader/business filters operate inside that context. Switching ticker is a deliberate, visible action that resolves a valid day and refreshes all dependent Review state.
- Candidate classification modes for later design selection:
  - Ticker tabs + date rail (preferred current direction): persistent SPY/QQQ segmented tabs at the top of the context panel, followed by a compact month-grouped rail containing only the selected ticker's dates. Fast switching and lowest visual cost.
  - Collapsible ticker groups: separate SPY and QQQ sections, each owning its own recent-date list. Makes inventory visible but risks recreating mixed-symbol scanning when both groups are expanded.
  - Ticker workspace landing: two clear SPY/QQQ workspace entries followed by a dedicated date browser after selection. Strongest separation, but adds an extra navigation step before every review.
- Availability-driven trader rule: after resolving ticker and date, derive the visible trader controls from actual displayable trade groups in that context. A trader with no point/group for the selected ticker/date must not appear by name and must not retain a checkbox or Focus control. If no trader has a point, hide the trader-option list and use a neutral empty state rather than showing the global registry. Switching ticker/date clears or intersects stale `traderIds` and `focusedTraderId` before rendering chart markers, statistics, or exports.
- Information-architecture boundary: this is UI/workflow isolation, not physical data segregation. The tracked SQLite schema, SPY/QQQ same-provider pair orchestration, candidate rebuild, integrity/non-shrink gates, canonical trade storage, and Pages publication inputs remain shared unless a separate governed decision explicitly changes them.
- Acceptance direction: a user can tell whether they are in SPY or QQQ before choosing a date; default Data and Review lists never interleave symbols; a Data-page day selection opens/reconciles Review to the same ticker/day; switching ticker cannot leave stale chart, signal, unavailable trader names, statistics, or export state from the prior ticker; an explicit future comparison mode, if desired, is separate from the default workflow.
- Accessibility risk: the ticker workspace selector must have a programmatic group label, visible selected state, and predictable focus/state-change behavior. Color or ticker logos alone must not carry the distinction; screenshot evidence alone cannot verify keyboard or screen-reader behavior.
- Boundary that must not change: do not fabricate missing QQQ/SPY dates, silently substitute one ticker for another, weaken pair/provider/data gates, or relabel a UI partition as database isolation.
- Lifecycle status: proposed via [`Tang Strategy Review Workspaces And Trader Point Editing`](../exec-plans/proposed/2026-07-19-tang-strategy-review-workspaces-and-trader-point-editing-plan.md); review-only

## OPT-004 Keep Interactive And Static Review Governance Aligned

- Source evidence: `.github/workflows/publish-static-reviews.yml` exports review JSON and builds with `VITE_STATIC_REVIEWS=true`; `frontend/src/main.jsx` then renders `StaticReviewsApp` instead of the authenticated application shell. A 2026-07-19 local `/tmp` rehearsal against the current tracked DB exported and built successfully with 49 review days and 9 strategies: 46 SPY days plus 3 QQQ days in one flat manifest, ordered with QQQ 2026-07-17 first. `frontend/src/pages/StaticReviewsApp.jsx` renders that flat mixed-symbol list and repeats 1m/5m, Back, Step, Play/Pause, and Overview outside the K-line engine.
- Current static effect: GitHub Pages is a standalone Review surface, not a static copy of the full local application. It has no login, Data dashboard, Backtest, Teaching, or Admin/trader editing workspace. With the current branch's data it would default to QQQ 2026-07-17, mix all 49 SPY/QQQ days in one sidebar, and retain the duplicated chart controls. QQQ 2026-07-17 and 2026-07-10 export two verified trader groups each; QQQ 2026-07-14 exports the market day but zero trader groups because its record remains pending and static export admits verified records only.
- Desired outcome: interactive Review and Static Review share one product-level contract for ticker workspace selection, market-day context, strategy selection, availability-driven trader/business filters, and K-line control ownership. Static mode may remain Review-only, but its intentional capability differences must be explicit rather than allowing a second UI implementation to drift.
- Acceptance direction: the same SPY/QQQ partitioning, unavailable-trader suppression, and single-owner control rules pass in both implementations; a static deep link resolves ticker/day deterministically; legacy day hashes continue to open or receive an explicit compatibility decision; static mode never exposes admin mutation; verified-only trade visibility is clearly represented; interactive/static fixture tests prove selection, chart, signal, trader marker, and export reconciliation.
- Evidence limit: the 2026-07-19 rehearsal verified export contents and a production static build in `/tmp`; it did not publish or visually inspect the hosted GitHub Pages site. The current hosted site remains whatever is already published from `main`.
- Boundary that must not change: local build or fixture parity does not authorize a push, Pages workflow, `gh-pages` update, hosted verification, or any remote action. Publication remains a separate explicit gate.
