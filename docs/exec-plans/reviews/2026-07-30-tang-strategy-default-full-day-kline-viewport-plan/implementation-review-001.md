## Verdict Rationale

**Diff scope and data safety — verified.** `git show f667867 --stat` touches exactly five files, all under `frontend/src/`: `kline-engine.js`, `engineOptions.js`, `reviewWorkspace.test.js`, `ReviewPage.jsx`, `StaticReviewsApp.jsx`. No `data/`, `backend/`, `content/`, or DB path appears in the commit. `frontend/src/kline/UnifiedKlineEngine.jsx` and `frontend/src/features/review/TraderPointEditor.jsx` are confirmed untouched by the commit and by re-reading their current content: `UnifiedKlineEngine.jsx` already forwards the entire `engineOptions` object opaquely to `new KlineEngine({... options})` and to `engine.setOptions()`, so no wrapper change was needed to carry `initialViewport` — the "only if required" constraint in plan §3.6 is correctly honored by *not* touching that file. `TraderPointEditor.jsx` still imports and uses the unmodified `DAILY_REVIEW_ENGINE_OPTIONS` (no `initialViewport` key, so `_normalizeOptions` falls back to `DEFAULT_ENGINE_OPTIONS.initialViewport = 'default'`), matching the plan's requirement that non-Review/Static consumers keep default tail-window first paint. Tracked SQLite hash (`383cf9012...`) is unchanged and matches the pre-session value; `git status` shows it as the only dirty path, pre-existing and untouched by this commit. `git diff --check f667867^ f667867` is clean.

**Acceptance table — verified by trace, not by an independent browser run.** I hand-traced `fitAllAvailableBars()` → `fitRange({startIndex:0, endIndex:bars.length-1, paddingRatio:0, minPadding:0})` and confirmed `desiredCount = bars.length`, and — critically — that `getResolvedViewCount`'s `maxCount = Math.min(limits.maxBars, totalBars||1)` now equals `totalBars` exactly (because `getViewLimits` sets `maxBars = totalBars` whenever `totalBars > 0`), so `clampedCount = clamp(bars.length, minCount, bars.length) = bars.length` for any payload length, not just 390/78. Feeding that into `getVisibleWindow` (unchanged code) with `followMode=false`, `viewStart=0` yields `maxEnd = totalBars-1`, `maxStart = 0`, `start = 0`, `end = totalBars-1` — exactly the acceptance row for first paint and Overview, for both 1m (390) and 5m (78), and for a variable-length payload (traced generically, not pinned to 390/78). The `setTimeframe()` branch for `initialViewport==='full'` sets `zoomScale = nextBars.length / viewInfo.base` so that `getResolvedViewCount` resolves to the same `count = totalBars` result after a timeframe switch; traced the same way with the same conclusion. `fitRange()` itself is unmodified by this diff — trade/signal-card clicks (`ReviewPage.jsx`/`StaticReviewsApp.jsx` callers, all omitting `paddingRatio`/`minPadding` and thus using the pre-existing 0.35/5 defaults) go through the exact same, untouched function body that `fitAllAvailableBars` merely calls with different explicit arguments; the delegation does not alter `fitRange`'s behavior for real (non-zero-padding) callers. `applyZoom` is unmodified code; for a standard 390×1m/78×5m RTH day, `getViewLimits`'s new formula (`totalBars>0 ? totalBars : fallback`) produces the *same* `maxBars` as the old `Math.min(390/78, totalBars||...)` formula, because `totalBars` never exceeds 390/78 on a normal day — so manual zoom-out ceiling is unchanged for the common case. The ceiling only rises above 390/78 when the payload itself has more bars than that (confirmed this happens in practice: `ReviewPage.jsx`'s "Ext K" toggle loads a 09:00–16:30 window via `reviewPayloadForWindow(review, 'extended_k')`, which is longer than the 09:30–16:00 RTH window), and removing the old cap is *necessary* for `fitAllAvailableBars` to genuinely fit "every available bar" on those extended-session payloads — without it, `fitRange`'s own `clampedCount = clamp(desiredCount, minCount, maxCount)` would silently truncate to 390/78 even after this commit. This is a required, not incidental, part of the fix, and does not change zoom behavior for the ordinary RTH case a user would call "normal."

**No stray hard-coded 390/78 values drive the new logic.** The only remaining `390`/`78` literals in `getViewLimits` are an explicit `fallback` used solely when `totalBars` is falsy (i.e., before any data has loaded) — harmless, and consistent with plan §3.5's "do not implement the behavior with... hard-coded 390/78 values," since the *behavior* (first paint, Overview, timeframe switch) is driven entirely by the payload's actual bar count.

**`overview()` is intentionally engine-global, not Review/Static-gated**, per plan §3.2 ("Make `overview()` use that operation instead of `ViewportManager.reset()`" — an unconditional instruction) and per the plan's own framing that the Overview button already promises "fit the full day" for every consumer. This means Teaching's and Backtest's Overview button (and Teaching's "Reveal full day" button, which calls `engine.overview()`) now also fit-all instead of resetting to a tail window; `initialViewport` remains the only Review/Static-scoped knob, governing first paint (`loadData`) and timeframe switches (`setTimeframe`) only. I verified this asymmetry is deliberate and matches the plan text, not scope creep.

**Regression surface checked and clear.** `play()`, `stepForward()`, `stepBack()`, and `_advanceTo()` all unconditionally force `followMode = true`, so `overview()`'s new `followMode=false` side effect cannot leave Teaching/Backtest's playback stuck in a non-follow state — any subsequent step or play call restores follow immediately. Teaching's `step()`/`revealAll()` explicitly pass `{follow:true}` to `setCurrentIndex`, independently re-asserting follow. Price/volume scaling and the render pipeline (`render()`, `buildRenderContext`) are untouched by this diff and consume only `visible.start/end/count` from the unmodified `getVisibleWindow`, so they are structurally unaffected by a wider viewport count.

**Independently confirmed the reported pre-existing Teaching bug and its non-applicability here.** `TeachingPage.jsx` passes only `payload`/`ref`/`onReady` to `<UnifiedKlineEngine>`, never `annotations1m`/`annotations5m`; `UnifiedKlineEngine.jsx`'s default parameters (`annotations1m = []`, `annotations5m = []`) therefore construct a new array identity on every re-render, which changes the `payloadWithAnnotations` `useMemo`'s dependency identity every render and re-fires the `loadData()` effect. This is pre-existing: the diff shows `loadData()`'s non-`'full'` branch already called `this.viewportManager.reset()` unconditionally before this commit, so Teaching (which stays on `initialViewport:'default'`) was already subject to this re-entrancy before and after this change — it is orthogonal to this plan. `ReviewPage.jsx` and `StaticReviewsApp.jsx`, by contrast, both pass `engineAnnotations1m`/`chartAnnotations5m` built via `useMemo` with stable dependency arrays (including a literal `useMemo(() => [], [])` for the always-empty 5m annotations), so their `annotations1m`/`annotations5m` props are reference-stable across unrelated re-renders and are not subject to this bug. The claim in the task brief is correct.

**One real gap, non-blocking.** The single updated test is a source-string/shape pin, not a runtime/behavioral test — it would not catch a regression in the actual arithmetic this commit introduces (e.g., a broken `getViewLimits` totalBars branch, or a broken `setTimeframe` zoomScale computation), and no committed browser-acceptance script backs the acceptance table either. This is real and worth a documented follow-up (see Findings), but it is a coverage-durability concern, not evidence of a live defect: I independently re-derived the correct numeric behavior via static trace of the actual current file (not by trusting the author's summary or the test), and the automated suite/builds that do exist all pass. It does not rise to P1 because nothing in the traced behavior is actually wrong.

**What remains unverified.** I did not open a browser or drive the dev server myself this session, so I cannot independently corroborate the exact pixel/DOM rendering or click-driven Overview button flow end-to-end — only the underlying viewport arithmetic those flows depend on, which I traced directly against the current source rather than trusting the commit message or the author's reported live values. Given the small, well-contained diff and the precision with which the arithmetic could be traced to the acceptance table, I have high confidence in this verdict despite not running a browser myself.
