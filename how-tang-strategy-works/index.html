03

它们怎么对话

登录像办门禁腕带：先换通行证，再每次请求都出示。

腕带规则：没带就别进

你已经认识演员了。现在看他们怎么说话：密码换 token，请求头带上，后端才肯拼复盘包。

前端frontend 从不直接打开数据库；它只喊 API 路径。后端校验身份后，从 SQLite 拼出 bars、strategy、trade_records。

🎫
Bearer token = 门禁腕带

Authorization: Bearer <token> 不是「问候语」，是每次进门要亮的腕带。丢了腕带 = 401 Unauthorized，和「图是空的」完全不是一回事。

一次请求的生命周期

从密码到复盘 JSON，固定五步。任何一步断了，症状都不同。

1
POST /auth/login

浏览器把密码 JSON 发给后端；密码对了才换腕带。

2
存 token + role

localStorage 记下 token 和角色（admin / readonly）。

3
api() 自动贴腕带

之后每个请求头都加 Authorization: Bearer …。

4
GET /api/reviews/assemble

后端 require_readonly 验身份，再查 day / strategy / bars。

5
返回复盘包

一份 JSON 里装 1m/5m K 线、策略体、当日交易记录——前端只负责画。

代码在说什么：换腕带 + 亮腕带

login 负责办证；api() 负责每次出门都把证贴在袖口。

CODE 
export async function login(password) {
  const response = await fetch(`${API_BASE}/auth/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ password }),
  });
  if (!response.ok) throw new Error('Password rejected');
  const data = await response.json();
  window.localStorage.setItem(TOKEN_KEY, data.token);
  window.localStorage.setItem(ROLE_KEY, data.role);
  return data;
}
 
export async function api(path, options = {}) {
  const token = getToken();
  const response = await fetch(`${API_BASE}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...(options.headers || {}),
    },
  });
白话对照

login：拿密码去服务台换临时通行证。

密码不对 → 直接抛错，不发腕带。

成功后把 token 和 role 塞进浏览器抽屉（localStorage）。

api(path)：每次请求先摸口袋有没有 token。

有 token → 请求头写上 Bearer …，像亮腕带。

没 token → 不带 Authorization，后端大概率 401。

两种腕带颜色

密码对照用 hmac.compare_digest，对上 admin 或 readonly 之一才算身份。

admin 管理员腕带：可写导入、改内容等管理接口
readonly 只读腕带：够看复盘、拉列表；assemble 最低要求就是它
None 密码都不对 → 不发腕带，后续请求被拒
🔐
role_from_password

后端用常量时间比较密码，返回 "admin" / "readonly" / None。腕带颜色决定你能喊哪些 API——不是前端自己声明的。

🚫
401 / 鉴权失败

腕带没了、过期、或根本没登录——请求在打包前就被拦下。

📦
404 Strategy / Market day

身份过了，但 day 或 active strategy 对不上——包打不出来。

200 但图是空的

场景测验：先分清故障层

三题都是「你看到什么症状，该先查哪一层」——不是背路径名。

1. 用户清掉 localStorage 后再点复盘，最可能先看到什么？

2. 同事能登录但只能看图，导入接口 403。你该先核对什么？

3. 网络里 assemble 返回 200，策略名也在，但 K 线区域完全空白。优先查哪条？

⚡
指挥 AI 时用对词

说「401 鉴权」/「404 strategy」/「200 但 bars 空」，AI 才不会在登录页、策略表、画图引擎三处乱打补丁。

04

数据保险库

银行金库：草稿纸是 seed，总账是 SQLite，公开宣传册是 Pages。

复盘包从哪装货？

上一课：API 从库里打包。这一课：库本身怎么进货，公开静态站又读谁。

唯一运行时真相是被 Git 跟踪的 tracked SQLite。seed 只是本地抓取输入；Pages 是从同一本总账导出后再构建。

data/
seed/market-data/live_extended/ 受理窗口的临时单据（抓取输入）
sqlite/
tang_strategy_live_extended.db 金库总账 · 运行时真相
content/trades/ 规范交易原文（canonical），不是草稿
frontend/public/reviews/ 导出 JSON · 构建输入，不是真相源

进货流水线：从单据到宣传册

默认路径永远是「候选库 → 校验 → 原子晋升」。不许跳步把半成品直接当总账。

1
Seed JSON

live_extended/<date>/ 成对 SPY/QQQ 单据；本地抓取写入，不进公开站。

2
Candidate DB

重建先写候选库；日期缩水等硬门一失败就拒收。

3
Live tracked DB

校验通过后原子 promote——这才是 runtime 真相。

4
Export static JSON

从 live DB 导出 slug 文件；Pages 读的是这份拷贝，不是 seed。

5
StaticReviewsApp

静态模式挂载公开宣传册：无登录、无编辑，只浏览导出结果。

🚫
生成物不进 docs/

静态 review JSON、Vite dist、Pages 产物都不是文档。故意存档的 OPT 截图/验收钉可以跟记录走；构建输出禁止写回 docs/。

两套壳，同一套导出/总账约定，不要混着改。

interactive 登录 + Bearer + 调 live API；可编辑/导入（视角色）

content/trades 交易规范原文；入库是投影，改交易先改这里
seed JSON 本地抓取输入；只改 seed 不 rebuild = 总账不变

三层分清就不怕 AI 写错地方

场景测验：数据源与回落

发布错数据，多半是把 seed、总账、宣传册搞混了。做完这三题再指挥 AI。

1. 公开 Pages 上的 SPY 复盘，数据源实际是什么？

2. 静态站 URL hash 写成不存在的日期时，合理行为是？

3. 要修正某日公开复盘上的成交点位，第一落点应是？

宁可失败也不乱写

空管塔台换跑道：新航班计划必须全部过检，旧跑道先备份；半空发现问题就立刻切回备份。

为什么「有一个就算了」不行？

每天都要更新 SPY + QQQ 这对标的。抓取失败、质量门没过、半路断电——这时候旧库必须完好。

核心原则叫 fail-closed ：宁可整次更新失败，也不接受「只写进一半」的生产库。

🛡
fail-closed vs fail-open

fail-closed：门没过 → 拒绝写入 → 旧 live 继续服务。
fail-open：门没过 → 硬塞进去 → 半套数据污染生产。
Tang Strategy 的日常路径永远是前者。

塔台换跑道：四步

把更新想成空管切换跑道。 candidate 是新计划，live 是正在使用的跑道，backup 是随时可切回的旧跑道副本。

1
Stage pair — 成对进场

orchestrator 要求 PAIR = ("SPY", "QQQ") 同一天、同一 provider 。只到一个标的 = 整批拒绝。

2
Validate — 硬门检查

会话模式、provider 一致、bar 质量等 hard gate 必须全过。TV 优先；IB 只在 TV 重试与硬门失败之后才作为后备。

3
Build candidate — 新跑道旁建

在旁路建好完整 candidate，并先做好 live 的 verified backup。candidate 还没 promote 前，用户仍读旧跑道。

4
Promote OR keep old — 授权落地或原路返回

锁住 live → 确认没漂移 → os.replace → fsync → post_validate 。验证失败立刻把 backup 换回 live。

成对常量：同一天、同一源

编排器写死了这对关系。日常路径禁止「只收 SPY」「混用两个 provider」「默认 --allow-date-loss」。

Code 
PAIR = ("SPY", "QQQ")
SESSION_MODE = "extended"
PROVIDERS = {"tradingview", "ibkr"}
TRADINGVIEW_EXCHANGES = {
    "SPY": "AMEX",
    "QQQ": "NASDAQ",
}
Plain English
PAIR — 永远成对：SPY 与 QQQ 同进同退
SESSION_MODE — 扩展时段会话，不是任意字符串
PROVIDERS — 只认这两个源：TV 优先，IB 后备
TRADINGVIEW_EXCHANGES — 各标的在 TV 上的交易所代码
tradingview first 日常默认源；不因 Gateway 关闭就去找 IB
ibkr fallback 仅在 TV 重试或硬门失败后，报告失败门再请开 Gateway
never --allow-date-loss 日常/默认路径禁止用丢日期换「强行通过」

promote_candidate：签名在说什么

推广不是「覆盖文件」那么简单。函数要同时拿着 live、candidate、baseline 令牌、backup 和推广后校验回调。

漂移拒绝：live 在快照后被改了？

锁住写入后先检查：live 是否还是你开建 candidate 时那一份。若别人/别进程在中间改过，直接拒绝推广。

db_write_lock — 独占跑道，防止双写
_checkpoint_and_require_quiescent — 要求库安静、可安全替换

RuntimeError — 拒绝推广，candidate 不上线

落地与回滚：一秒钟的生死线

令牌对上了，才做原子替换。替换后立刻再验；任何异常都把 backup 换回 live，再把异常抛出去。

Code 
os.replace(candidate, live)
fsync_directory(live.parent)
try:
    post_validate(live)
except Exception:
    os.replace(backup, live)
    fsync_directory(live.parent)
    raise
Plain English
os.replace(candidate, live) — 原子改名：新跑道就位
fsync_directory — 把目录改动刷盘，防断电丢名
post_validate(live) — 替换后再跑业务硬门
except — 任一失败进入回滚通道
os.replace(backup, live) — 旧跑道立刻复位
raise — 不吞错误；调用方必须看见失败
✈

新计划可以作废，旧跑道不能没。这就是 fail-closed 在数据库推广上的具体形状。
