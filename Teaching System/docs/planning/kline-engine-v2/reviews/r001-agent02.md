# 交付物评审意见

**审核对象**：kline-engine-v2-plan.md

## 整体判断
**裁决**：revise
**置信度**：medium

## 总体评价

这份方案的方向判断是成立的。文档准确识别了旧版 `kline-sandbox.html` 的核心问题：教学逻辑、preheat、annotation 交互和渲染引擎混在一起，确实不适合直接拿去做 daily-review。相较于“边拆边修旧引擎”，单独规划一个 v2，并把视觉规范、模块划分、公共 API 和任务顺序一次性写出来，是更稳的做法。

优点也比较明显。第三章把深色券商风格拆到了颜色、K 线几何、坐标轴、十字线、缩放手感这些可执行粒度；第四章把 DataManager / ViewportManager / Renderer / Playback / Annotation / EventBus 分开，说明作者已经在主动避免旧版“全局 state + 散落函数”的问题；任务分解也基本遵循从骨架、渲染、交互到 API 的推进顺序，便于执行。

但当前版本还没有达到“可以直接开工且不会在 Phase 2 再返工”的状态。主要阻断点有四个：交付物形态与 daily-review 主计划的消费方式没有闭环；视觉验收标准自相矛盾；`scrollTo(barIndex)` 在 1m/5m 双时间框架下契约不完整；验证数据只用教学 seed，覆盖不到 full-day 目标场景。以上问题不需要推翻重写方案方向，但需要先修文档。

## 问题清单

### 严重问题

1. **交付物形态与 daily-review 的消费方式没有闭环**
   - 位置：二、产出；五、Task 6；`daily-review-plan.md` 的“五、预计目录结构”
   - 问题描述：当前文档把产出定义为 `dist/kline-engine-v2.html` 单文件 HTML，并写成“可被 daily-review 直接复制使用”。但 `daily-review-plan.md` 已经把消费方定义为独立的 `Daily review/dist/daily-review.html` 页面。现在没有说明 daily-review 将如何使用这个 v2 引擎：是复制整页 HTML、抽出其中的脚本、用 iframe 嵌入，还是通过 `window.KlineEngine` 之类的挂载协议实例化。Task 6 虽然列了 `loadData()/on()/scrollTo()` 这些 API，但没有定义外部页面如何拿到 engine 实例，也没有定义宿主页面必须提供哪些 DOM 容器和样式钩子。
   - 影响范围：这会导致“v2 引擎已完成”与“daily-review 可直接复用”之间出现断层。最坏情况是先做出一个漂亮的独立 demo，后续接入 daily-review 时还要再做第二次结构改造，前置工作的价值被削弱。
   - 改进建议：先把复用契约写死，再开始实现。至少明确以下其一：1）`kline-engine-v2.html` 只是演示页，真正可复用的是页面内暴露到 `window` 的 `KlineEngine` 类和固定的 mount 协议；2）daily-review 将直接复制某一段受标记保护的 HTML/CSS/JS 区块；3）改为“单文件 demo + 单文件 embeddable engine”双产物。文档里需要把消费方式、宿主要求和责任边界写清楚。

2. **视觉目标与验收标准前后冲突**
   - 位置：三、视觉规范；Task 2；Task 7 最后一条
   - 问题描述：文档前半部分要求“对标 moomoo 券商风格”，并在 Task 2 明确写了“视觉层面全部重写为券商风格”；但 Task 7 的验收又写成“与旧 sandbox 视觉对比无明显差异（K 线样式、颜色）”。这两个标准不能同时成立。现有 `kline-sandbox.html` 实际是浅色米白主题，颜色、边框、OHLC overlay 和整体气质都与第三章定义的深色券商界面差异很大。
   - 影响范围：执行者无法判断到底该追求“行为一致、视觉重写”，还是“连颜色和样式也尽量贴近旧版”。同一份实现可能被一个 reviewer 认为“改得不够像 moomoo”，被另一个 reviewer 认为“改得偏离 sandbox 太多”。
   - 改进建议：把验收标准拆成两条互不冲突的基线。建议改为：1）交互数学和绘制行为与旧 sandbox 对齐（缩放、坐标、DPR、bar 对齐）；2）配色、布局层次、标签样式与 moomoo 参考图对齐。不要再使用“与旧 sandbox 视觉对比无明显差异”这种会覆盖掉视觉重写目标的表述。

3. **`scrollTo(barIndex)` 与标注索引契约不完整，无法支撑双时间框架联动**
   - 位置：四、与旧版的关键差异；Task 5；Task 6；六、数据格式
   - 问题描述：当前 API 只定义了 `engine.scrollTo(barIndex)`，标注格式也只有 `bar_index`，但引擎同时支持 `bars_1m` 和 `bars_5m`，外部 UI 还要处理信号列表、5min 趋势时间线、1m/5m 切换。此时单独传一个裸 `barIndex` 是有歧义的：如果用户当前停在 5m，而外部侧栏点的是 1m 信号，该跳到 1m 的第 142 根，还是当前时间框架的第 142 根？是否要自动切换时间框架？是否需要高亮目标 bar？文档都没有定义。
   - 影响范围：这是 daily-review 最核心的“列表点击跳图表”接口。如果契约不写清楚，Phase 2 很容易靠隐式假设先糊出来，后续再因为联动错误返工。
   - 改进建议：把跳转协议改成带语义的接口，例如 `scrollTo({ timeframe, barIndex })` 或 `scrollToTime(timestamp)`，并在文档中明确点击 1m/5m 来源项时的切换行为、目标 bar 居中策略和是否同步更新 playback/currentIndex。

4. **验证数据与目标场景不匹配，当前验收无法覆盖 full-day 引擎**
   - 位置：Task 1；Task 7；七、关键文件
   - 问题描述：文档把 `teaching_segments.json` 中的 `seed_01` 作为开发和端到端验证数据来源，但本地数据里 `seed_01` 只有 67 根 1m bar、33 根 5m bar、3 个 1m 标注和 1 个 5m 标注。这与第三章、Task 4/5/7 想验证的目标场景明显不一致：计划要求最多显示全天 390 根 K 线、所有已过标注同时可见、播放和缩放在 full-day 上保持流畅。用一个教学切片做唯一验收样本，无法覆盖这些关键条件。
   - 影响范围：如果按当前计划执行，很可能在教学 seed 上全部通过，但到了 daily-review 的整天 SPY 数据上才暴露出缩放边界、标注密度、性能和布局问题，前置验证失去意义。
   - 改进建议：把验证数据分成两层。`seed_01` 只保留为 smoke test；另增一个 full-day 390-bar 级别的 fixture 作为主验收数据，优先使用 daily-review 管线产出的真实日数据，至少也要用合成数据把 bar 数量、成交量区、annotation 数量和 1m/5m 切换压满。

### 中等问题

1. **标注渲染策略没有写清，性能与可读性风险被低估**
   - 位置：Task 5；九、风险
   - 问题描述：Task 5 明确要求“所有已过 bar 的标注同时可见”，但没有说明这些标注是继续沿用旧 sandbox 的 DOM 气泡方案、改成 canvas 图元，还是做可见区域裁剪。现有 sandbox 的 annotation 是在每次 render 时清空并重建 `.anno-bubble` DOM 元素；如果 v2 默认沿这条路线走，full-day 多信号场景下，缩放和拖拽时的重排、遮挡和阅读噪声都会明显上升。当前风险表也没有覆盖这一点。
   - 影响范围：即便功能正确，也可能出现卡顿或“标注全挤在一起看不清”的结果，直接影响 daily-review 的可用性。
   - 改进建议：在 plan 中先选定策略，例如“画布上只绘制 pin/箭头，详情用 hover panel 展示”，或者“DOM 气泡只保留高分/当前窗口内的前 N 个，其余折叠为计数标记”。同时把“多标注拥挤与性能退化”补进风险表。

2. **moomoo 参考物没有固化为可核对资产，视觉评审仍偏主观**
   - 位置：三、视觉规范；Task 2 验证
   - 问题描述：文档写了“参考：moomoo 2026-04-13 SPY 1min 截图”，但当前计划里没有这张截图的本地路径、裁切区域、尺寸信息，也没有冻结最终 token 取值，部分颜色仍写成“`#00b894 或 #2ecc71`”这种二选一表述。这样会让“接近 moomoo”停留在描述层，无法形成稳定的 review 基准。
   - 影响范围：不同执行者对“券商风格”的理解会出现漂移，后续复审只能做主观判断。
   - 改进建议：把参考截图作为文档资产固定下来，至少写明文件路径或附图位置；同时把色值、线宽、标签背景等关键 token 收敛成唯一取值，避免执行时自由发挥。

### 轻微问题

- 无

## 未验证项

- **本轮核查资料边界未被协调者显式指定**：本次审阅按文内引用和同目录规划文件做最小核查，实际使用的本地依据为 `kline-sandbox.html`、`teaching_segments.json`、`daily-review-plan.md`。超出这些文件的事实性陈述，仅能做结构审阅，不能视为已完成事实核查。
- **moomoo 参考截图本体**：文档提到了截图，但当前未提供可读取的本地图片或链接，无法验证第三章中关于视觉贴近度的细节描述。
- **真实 full-day daily-review 数据表现**：当前只核查到了教学 segment 数据，尚未拿到 daily-review 计划中提及的完整日数据，无法验证 390 bar、较多 annotations 和真实信号密度下的交互表现。
- **“约 40% 代码是教学专用”这一比例判断**：旧 sandbox 确实存在 preheat、annotation、章节/segment 选择等教学逻辑，但 40% 这个比例未在核查资料中给出统计依据，只能视为经验判断。

## 裁决理由

本轮裁决为 **revise**。

原因不是方案方向错误，而是文档里还存在会直接影响执行闭环的结构问题。最核心的四项阻断分别是：v2 引擎到底如何被 daily-review 消费没有定义清楚；视觉验收标准自相矛盾；跳转 API 在 1m/5m 联动下缺乏明确契约；验收样本没有覆盖真正的 full-day 使用场景。这些问题一旦带着模糊状态进入实现，后面几乎必然返工。

建议先补齐“复用协议 + 验收口径 + 跳转契约 + full-day fixture”这四块，再进入编码。完成这轮修订后，这份 plan 仍然有很大概率可以进入执行，不需要推翻整体方向。
