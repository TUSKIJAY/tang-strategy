# 交付物评审意见

**审核对象**：kline-engine-v2-plan.md（R1 修订版）

## 整体判断
**裁决**：revise
**置信度**：high

## 总体评价

R1 修订版明显比上一轮成熟得多。上轮我指出的四个核心阻断点里，三个已经实质收口：`scrollTo` 契约补全到了跨时间框架级别，Task 7 也补上了 full-day 390 bar 主验收数据，行为验收与视觉验收的口径也被拆开，不再互相打架。与此同时，Task 1 前置 EventBus、Task 5 选定 Canvas pin + Hover 详情、风险表引入性能预算，这些都不是表面修辞，而是会直接减少后续实现返工的工程化改进。

这版文档的另一个优点，是把“为什么要重写而不是剥离旧引擎”讲得更准确了。背景对旧 sandbox 的描述已经从粗糙的“单体 + 教学代码很多”修正为更贴近事实的过程式架构 + 局部教学耦合，说明作者是在用核查结果修 plan，而不是仅仅照抄 review 建议。

但当前版本仍然没有完全达到可执行状态。剩下的问题不多，却都落在“集成契约”和“验收基线”这两个关键层面：消费协议仍未把样式交付方式写闭环，moomoo 参考图仍未固化为仓库资产，而文档却已经把截图对比写进了执行和风险缓解。换言之，方案的主体已经基本成型，但还差最后一层“执行者不需要猜”的封口。

## 问题清单

### 严重问题

1. **消费协议只闭环到 JS，未闭环到样式资产** [修订引入]
   - 位置：第二章「产出与消费协议」L45–49
   - 问题描述：文档现在规定宿主页面只需提供容器，引擎负责在容器内创建 canvas、controls、overlays 等 DOM；同时又写明引擎的 JS 和 CSS 都内联在 `kline-engine-v2.html` 中，但 daily-review “如需独立引用，从中提取 `<script>` 块即可”。这三个表述放在一起是自相矛盾的：如果宿主只提取 `<script>`，而 CSS 仍停留在 demo 页的 `<style>` 里，那么引擎生成出来的 controls / overlay / hover 面板将没有样式来源。除非脚本负责运行时自动注入样式，但文档没有写这一点。
   - 影响范围：这会直接影响 v2 作为 daily-review 前置工作的核心价值。当前协议看上去已经能嵌入，但执行者真正落地时仍要自己猜“到底是提 script、提 script+style，还是让 constructor 注入 style”，集成仍有返工风险。
   - 改进建议：把样式交付方式写死，三选一即可：1）`KlineEngine` 构造时自动向 `document.head` 注入一次带命名空间的 `<style data-kline-engine>`；2）宿主必须同时引入引擎 `<style>` 和 `<script>` 两个片段；3）明确改成“双产物”方案（demo HTML + embeddable JS/CSS）。在文档里把宿主职责更新成可执行契约，不要再保留“提取 `<script>` 即可”的模糊说法。

2. **moomoo 参考图仍未固化为可复验资产** [遗留未修]
   - 位置：第三章标题下注释 L55；Task 2 验证 L201；风险表 L361
   - 问题描述：上一轮 review 已明确指出 moomoo 参考物没有落成仓库资产。本轮虽然把色值固定了，但文档仍然把“截图对比审查小字号标签可读性”和“对比 moomoo 参考图”写入执行步骤与风险缓解，而仓库中仍找不到这张 `moomoo 2026-04-13 SPY 1min` 参考图。
   - 影响范围：这使得 Task 2 的视觉验收和风险表中的可读性校验缺少统一基线。执行者、reviewer 和后续维护者都无法基于同一张图做复验，结果只能退回到“凭感觉像不像”。
   - 改进建议：把参考图以固定路径纳入仓库，例如 `docs/planning/kline-engine-v2/assets/moomoo-spy-2026-04-13-1m.png`，并在第三章或关键文件表中写明路径。若暂时无法入库，就把所有“截图对比”表述改成“对照外部参考图人工比对”，不要写成可复验资产。

### 中等问题

1. **公共协议暴露了 `theme: 'light'`，但方案并未覆盖 light theme** [修订引入]
   - 位置：第二章消费协议示例 L32–35；第三章视觉规范全文；Task 2 / Task 7
   - 问题描述：消费协议现在把 `theme: 'dark' | 'light'` 暴露成公开参数，但整份文档从视觉 token、Task 2 UI 适配、Task 7 验收到风险表，全部只定义了深色主题，没有任何 light theme 的设计 token、行为差异或验收口径。这意味着协议层已经对外承诺了一个未被计划覆盖的能力。
   - 改进建议：如果当前阶段只做 dark，就把示例和 API 说明改成仅支持 `theme: 'dark'`，或明确 light 为后续扩展、当前不实现。不要在 plan 阶段把未定义的能力挂进公开接口。

### 轻微问题

1. **关键文件表未纳入本轮新增依赖文件** [修订引入]
   - 位置：第七章「关键文件」L326–332
   - 改进建议：既然 Task 1 明确依赖 `data/SPY_1min_2026-04-13.csv`，Task 2/风险又依赖 moomoo 参考图，关键文件表最好同步补上这两类输入，避免执行者只看这一节时遗漏依赖。

## 未验证项

- **style 注入是否计划在实现中完成**：当前文档未写明引擎是否会自动注入 CSS，因此无法判断“只提取 `<script>`”是笔误还是有意设计。建议在修订时明确，不要把这个决定留到编码阶段。
- **moomoo 参考图内容本体**：仓库内未找到对应截图，无法核验色值、字号和布局是否真的与参考图一致。建议补充资产后再做视觉复审。
- **full-day fixture 的 MA/VWAP 生成逻辑**：本轮已确认 `data/SPY_1min_2026-04-13.csv` 存在且为 390 行完整交易日数据，但尚未核验后续“合成 MA 和 VWAP”的具体算法与旧项目保持一致。执行 Task 1 时需要补一个 sanity check。

## 裁决理由

本轮仍给出 **revise**。

原因不是主体方案还有大问题，而是剩下的两个阻断点都位于执行闭环上：第一，消费协议没有把样式交付说清楚，导致“可嵌入引擎”这一核心承诺还差半步；第二，文档已经把 moomoo 截图对比写进了验证流程，但参考图仍不在仓库内，验收基线不稳定。除此之外，R1 已经修掉了上一轮绝大多数关键问题，说明方向是对的，且修订质量较高。

建议再做一次小修：补齐样式交付契约，固化参考图资产，同时把 `theme: 'light'` 从公开协议里删掉或降级为未来扩展。完成这三处后，这份 plan 基本就可以进入执行阶段。
