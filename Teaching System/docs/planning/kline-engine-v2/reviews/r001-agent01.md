# 交付物评审意见

**审核对象**：kline-engine-v2-plan.md

## 整体判断
**裁决**：revise
**置信度**：high

## 总体评价

本方案的 **核心设计意图清晰且合理**：从一个与教学逻辑深度耦合的单体引擎中解耦出通用 K 线渲染引擎，采用"重建而非剥离"策略，这在架构上是正确的决策。模块划分（DataManager / ViewportManager / Renderer / InteractionMgr / PlaybackMgr / AnnotationMgr / EventBus）层次分明，关注点分离到位，pub/sub 解耦的思路也为上层集成（daily-review）预留了良好的扩展性。视觉规范章节对 moomoo 券商风格的描述非常细致，从配色到 K 线呼吸感到缩放体验都有具体数值约束，这将有效指导实现阶段的视觉还原。

方案的 **主要优点** 包括：(1) 新旧引擎并行共存的策略降低了迁移风险；(2) 外部 API 设计（`loadData()`, `scrollTo()`, `on()` 等）为下游 daily-review 提供了清晰的集成契约；(3) 数据格式保持向后兼容，降低迁移成本；(4) 任务分解粒度适中，每个 Task 有明确的验证标准。

但方案在 **若干关键细节上存在事实性偏差和设计遗漏**，需修订后才能进入执行阶段。最突出的问题是：行数声明与实际不符、对旧版架构特征的描述有误导性、视觉规范与旧版规范的冲突处理未说明、以及执行计划中对跨 Task 依赖和回退方案的考虑不足。

## 问题清单

### 严重问题

1. **旧版代码占比声明与事实不符**
   - 位置：第一章「背景」
   - 问题描述：文档声称「当前 `kline-sandbox.html` 是一个 ~1300 行的单体 HTML」。实际核查，该文件为 **1327 行**（含空行和 HTML 标签），但纯 JavaScript 代码区间为 L246–L1323，约 1077 行。1327 行包含了 195 行 CSS 和 HTML 模板。描述为「~1300 行」在容差范围内可接受，但紧跟的「约 40% 代码是教学专用」声明 **严重高估**。
   - 影响范围：核查旧版代码，教学专用逻辑（segment 选择器、`loadSegment` 切换、`auto_pause` 注解阻断机制、`preheat` 暗化、教学分类数据的 `categories` 字段）约占 JS 代码的 15–20%，并非 40%。夸大会误导对重构工作量的评估——若认为 40% 需要剥离，实际上只有不到一半的量。
   - 改进建议：修正为准确描述，如「约 15–20% 的 JS 逻辑与教学场景耦合（auto_pause 注解阻断、preheat 暗化、segment 选择、分类系统）」。这不影响「重建优于剥离」的结论，但准确数据能让执行者正确预估复用量。

2. **缩放因子 1.12 声明与验证**
   - 位置：第三章「缩放与拖拽体验」
   - 问题描述：文档称「缩放因子 1.08（比旧版 1.12 更细腻）」。核查旧版代码 L1216：`const factor = e.deltaY > 0 ? 1.12 : 1 / 1.12;`，确认 1.12 确为旧版当前值。但文档将 1.08 作为「一定更好」的断言，未给出依据。缩放因子的选择与帧率、数据密度、用户习惯相关，1.08 可能导致「滚半天好像没变」的迟钝感。
   - 影响范围：这是执行阶段可以通过 A/B 测试调整的参数，但写入规范文档后会被执行者当作硬约束。
   - 改进建议：修改为「缩放因子默认 1.08，可调范围 [1.05, 1.15]，执行阶段根据实际手感微调」。

### 中等问题

1. **旧版架构描述「全局 state + 散落函数」过于简化**
   - 位置：第四章「与旧版的关键差异」表格
   - 问题描述：旧版虽未使用 class，但代码组织已有清晰的注释分区（`DATA`、`STATE & UTILITY`、`CANVAS RENDERING ENGINE`、`ANIMATION / REPLAY ENGINE`、`SANDBOX ADAPTER`、`INTERACTION HANDLERS`、`INIT`），并非「散落函数」。渲染上下文 `buildRenderContext()` 实际上是一个高内聚的工厂函数，viewport 管理（`getVisibleWindow`, `applyZoom`, `setFollowMode`）也有完整的逻辑闭环。
   - 改进建议：改为「基于全局 state 对象和注释分区的过程式架构，无 class 封装，模块边界通过函数命名约定隐式表达」。

2. **K 线实体「涨跌都用空心」与旧版不一致，缺乏迁移说明**
   - 位置：第三章「K 线绘制细节」
   - 问题描述：v2 规范要求「涨跌都用空心（仅描边），不遮挡穿过实体的均线」。但旧版 `drawCandles()` 实现为：**涨用空心（白底绿边）、跌用实心（红填充红边）**（L657–665：`bullFill: '#ffffff'` vs `bearFill: '#ef3f34'`）。这是一个明确的视觉变更，文档第七章 Task 7 验证清单却写了「与旧 sandbox 视觉对比无明显差异（K 线样式、颜色）」，形成内部矛盾。
   - 改进建议：(a) 明确声明这是有意的视觉变更，并从验证清单中移除自相矛盾的对比项；或 (b) 沿用旧版涨空心/跌实心方案。二选一，不可两头都写。

3. **深色主题切换的全局影响未评估**
   - 位置：第三章「主题与配色」
   - 问题描述：旧版使用浅色主题（`--bg: #f9f7f3`，白底），v2 切换到深色主题（`#1a1a1a` 黑底）。这不仅是配色变化，涉及：(a) 注解气泡（`anno-bubble`）的颜色体系需全面重写；(b) OHLC overlay 的背景样式完全不同；(c) 十字线颜色/对比度要重新设计。但方案只在 Task 2 说了「深色主题全面使用第三章配色」，没有为样式迁移分配独立工作项。
   - 改进建议：在 Task 2 或 Task 5 中增加明确的子任务：「重新设计注解气泡、OHLC overlay、进度条等 UI 元素的深色主题适配方案」。

4. **EventBus 放在 Task 6（最后）但其他模块已硬依赖**
   - 位置：第五章「任务分解」
   - 问题描述：Task 6 定义了 EventBus 和 `emit()`/`on()` 机制，但 Task 5 的 AnnotationManager 已要求 `engine.emit('annotation:click', anno)`。严格线性执行下，Task 5 无法使用尚未实现的 EventBus。类似地，Task 4 的 PlaybackManager 应触发 `playback:tick` 和 `playback:state` 事件。
   - 改进建议：将 EventBus 提前到 Task 1（骨架阶段），它是一个极小的 pub/sub 实现（约20 行），不值得单独成为一个 Task。Task 6 可以改为「公共 API 封装 + 集成验证」。

5. **测试数据策略存在隐患**
   - 位置：Task 1「内嵌一份测试数据（从 sandbox 复制 seed_01）」
   - 问题描述：旧版 `kline-sandbox.html` 的数据区（L250）以 `const data = {...}` 内嵌了 **全部 3 个 segment**（seed_01, seed_09, seed_10）连同 categories，这是一个巨大的 JSON blob（约 60KB）。v2 的 `loadData(json)` API 设计为外部传入数据，但 Task 1 说要「内嵌一份测试数据从 sandbox 复制 seed_01」——这意味着要从那个 blob 中手动提取 seed_01 的数据并转换为 v2 格式。方案没有说明提取方式和格式转换步骤。
   - 改进建议：明确说明：(a) 编写一个提取脚本从 `teaching_segments.json` 中导出 seed_01 为 v2 数据格式；或 (b) 直接从 sandbox 的大 JSON 中手工裁剪。推荐 (a)，因为后续 daily-review 阶段也需要数据格式转换。

6. **缺少性能预算约束**
   - 位置：全文
   - 问题描述：旧版 sandbox 在 1m 时间框架下最大显示约 67 根 K 线，v2 声称最多显示 390 根（全天）。在 Canvas 上渲染 390 根 K 线 + 4 条 MA 线 + 成交量柱 + 注解气泡，是否能保持 60fps？方案未给出性能预算。
   - 改进建议：增加性能约束：「全屏 390 根 K 线 + 4 MA + Volume 渲染必须在 16ms 内完成（60fps），否则缩减最大可见 bar 数量」。

2. **高低点标注在旧版中不存在**
   - 位置：第三章「十字线与信息面板」
   - 改进建议：明确标注为新增功能，并在 Task 分解中分配到具体 Task（建议 Task 2 Renderer）。

## 未验证项

- **moomoo 2026-04-13 SPY 1min 截图**：文档引用此截图作为视觉规范参考，但截图不在核查资料范围内，无法验证列出的配色值、双轴设计、缩放因子是否确实与 moomoo 客户端一致。 -- 建议将截图作为附件纳入项目 `docs/assets/` 目录，供执行者对照实现。
- **daily-review 阶段对 v2 引擎的具体集成方式**：方案提到「daily-review Phase 2 直接使用」，但 daily-review 的集成需求（它要暴露哪些 API？数据从哪来？）未在核查范围内。 -- 建议在 v2 plan 中增加一个「下游集成预期」简表，避免 API 设计偏离实际需求。
- **`teaching_segments.json` 的数据结构是否完全兼容 v2 数据格式**：文件存在（已确认），但未核查其内部结构是否与方案第六章定义的 `loadData()` 格式完全匹配。 -- 建议执行 Task 1 前先编写格式对照文档。

## 裁决理由

给出 **revise** 而非 approve 的主要依据：

1. **存在严重问题**（教学代码占比声明失真），虽不影响「重建」结论，但会误导工作量评估。
2. **Task 执行顺序存在硬依赖冲突**（EventBus 在 Task 6 但 Task 4/5 已需使用），若不修正将导致执行阶段被阻塞或产生临时 workaround。
3. **视觉规范内部矛盾**（K 线空心/实心声明与验证清单的「无明显差异」自相矛盾），执行者无法判断应以哪个为准。

以上 3 项在方案文档层面可快速修正（预计 30 分钟内），修订后可重新送审。整体方案架构合理、方向正确，修订量不大。
